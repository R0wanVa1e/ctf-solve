# 完整调用链与运行时真值

适用于多语言 APK、Flutter/JNI、多进程共享状态、加载期壳、自修改代码、Python/Electron 打包。找到末端比较后，先逆向追到用户输入，再求逆。

## 跨层链先画完整

为每段记录 `输入格式/长度 → 变换 → 输出缓冲/长度 → 消费者`，附实际函数、调用参数和观测值。检查 Dart/Java/Kotlin 的字符处理、MethodChannel 序列化、JNI、worker 服务、共享文件、dlopen 载入的最终库。只解末端 `final_check` 的原像可能是上游密文，不是用户要输入的 flag。

- Flutter AOT 的 Smi、未装箱 int、压缩指针、可选参数约定按调用点确认；两个 sublist 参数不保证同一种装箱方式。先以长度、ASCII 限制与调用参数交叉核对，别仅看立即数。
- Flutter 分析器需匹配 Dart 版本、snapshot hash、目标架构与 compressed-pointers 等构建标志；已有 blutter 输出时先复用同哈希产物。Windows 编译器存在不等于编译环境已初始化，MSVC 的 cl/link/SDK 需在同一构建进程里载入 vcvars；日志已完成反汇编与对象池生成，就继续业务分析，不反复重装工具。
- JavaScript `charCodeAt` 处理 UTF-16 code unit；`atob → decodeURIComponent → charCodeAt` 不能直接替换为 UTF-8 bytes 异或。Python `ord` 对非 BMP 字符也不等价于单个 JS code unit，明确字符域后再移植。
- 自定义密码按原代码的加减、XOR、移位/旋转、截断和轮顺序求逆；“像 TEA/DES/RC4”只作指纹。保留各段中间值，正向逐段与真实机器码对拍，定位首个分歧。

## 静态、脱壳与自修改的区分

`upx -d` 得到的文件不是运行时最终真值的保证。保留原件、脱壳文件和运行时 dump 的哈希；确认实际执行地址、映射方式、重定位、导入与最后一次写入。密码表、CRC、字节码可能在 TLS/init、加载器或补丁阶段被改写。

对于多次执行同一缓冲的 SMC，按 `解密 → patch → 执行 → 再 patch` 记录轮次；逐条解释型（TF 单步）里“每轮”=每条指令，版本数上千，只记 `(地址,明文)` 轨迹，不能逐版本 dump。Unicorn 验证时说明入口、内存映射、ABI、栈、寄存器、返回哨兵和系统调用桩。

跳过上游检查前先判它的**结果是数据还是门禁**：固件/注册机类题里，自校验摘要、派生 key、IPC 参数就是下游计算的输入，跳过不是降置信度而是算错值；只有纯身份/授权检查才可作为“真实例程局部验证”跳过。

补丁版若只为修依赖/观测可作为辅助；修改成功判断、密钥分支、输入限制后的“接受”不能验收原题。验证至少包含一个正确候选和一个同长度错误候选；原程序不可运行时明确缺口，用真实例程和结构约束提高置信度。

## 打包与环境

- PE 的 overlay、`MEI` cookie、`PYZ`、`python3xx.dll` 指向 PyInstaller；先提取业务脚本、常量和 code object，避免对整套运行库静态硬逆。`marshal` 不保证跨 Python 版本兼容，`dis` 的 opcode 也需匹配；优先匹配解释器或支持该版本的反汇编器。不要执行不可信 pickle/marshal 来“提取参数”。
- Electron/NSIS 先查 `resources/app.asar`，恢复请求签名的 JSON 序列化顺序、时间单位、时间截断、字符串编码和 padding。签名通过、业务校验通过、数据库执行成功是不同阶段；正常购买同样数据库连接失败时先诊断服务健康。
- 动态 dump 时用输入阻塞/断点保持进程存活；stdin 提前 EOF 会让程序在 dump 前退出。工具写数据库/缓存时使用可写副本。缺依赖尽量以兼容解释器或局部仿真解决，桩函数返回值必须与被测路径语义一致。

## 系统调用与陷阱时序校准

逐条解释或异常驱动（SIGTRAP/TF）时，模拟器的系统调用语义会直接改变解密 key 的状态：

- EFLAGS 初值按真实进程给（`0x202`，含 IF）；无效 fd 的 `read/close` 返回真实错误码（`-EBADF`），不能一律 0，返回长度也按实际字节数。
- TF 下 `syscall` 的陷阱发生在**下一条用户指令之后**：紧随的 `mov [ctx+保存槽], ax` 必须先执行，否则保存的返回值与真实不同。
- `syscall` 会改 RCX/R11，模拟器要同步；否则后续依赖它们的序列错位。
- 判据：先用一个独立小程序确认“TF + syscall 的陷阱位置”，再套到目标上；这类 divergence 不报错，只会静默解错。

## Windows 父子进程与原生例程复用

导入 `CreateProcess(CREATE_SUSPENDED)/VirtualAllocEx/WriteProcessMemory/ResumeThread` 时，分别确认谁提供数据、谁执行校验；被写入的私有 RW 区也可能只是密文数据，不能把跨进程写内存等同“写入 shellcode”。直接运行子进程失败，先检查启动参数、父进程注入状态、共享控制台和等待条件。

可用原生纯计算例程减少算法抄写，但先核实架构/ABI、输入缓冲、所有内存引用、IAT、重定位、TLS 与安全 cookie 的依赖；复制节不等于完成 PE 加载。优先受控子进程或局部仿真，避免将未知机器码直接映射进分析工具宿主。首选基址分配失败时显式处理重定位，不能随意换基址继续调用。

校验若只是长度 + FNV/CRC 等短哈希，找到匹配文本只能证明接受条件成立，不能证明文本唯一；候选仍需正向全链与错误样本对照。`throne/work/writeup.md` 是父进程供数、子进程解密/校验的案例，其硬编码 VA 和手工映射方式不作为通用装载器。
